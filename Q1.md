# Q1, Capacity Under a Burst

## Problem

We need to serve 10,000 outbound calls inside a 30-minute window. Average call duration is 40
minutes. Each active call holds a persistent WebSocket to a speech-to-speech model and runs its own CPU-bound audio processing, noise suppression and VAD, in-process for the life of the call. We are on GCP. The failure mode we care about is not the obvious one. Long before instances stop accepting connections, audio starts getting choppy on calls that are already in flight. Quality degrades before availability does.

## 

## Analysis

I will assume this is a compute resource issue. I am assuming this is not a networking issue from the outbound side (for outbound calls on PSTN, 64kbs x 10,000 = 640Mb/s, which is fine), and not from the persistent WebSocket side.

The instances handling the calls (does  audio processing, noise suppression and VAD), are not getting the required CPU time, hence the choppy audio.

## Detecting the problem
We can monitor the CPU loads and have a threshold that warns that the issue will happen or is happening, however scaling will not help the in-flight calls
We can instrument the audio processing to detect choppy audio and alert


## Possible solutions (when choppiness is detected or anticipated)
 Most of the load is probably due to handling the inbound audio (not the outbound response)


1. Reduce audio processing load by stopping noise suppression in the calls with low noise

2. Introduce some acceptable latency on some calls via using longer outbound prompts (or slowing them) or hold music

3. Introduce some acceptable latency by introducing some additional questions that are not required ( expecting a short answer)
4. Orchestrating the calls so that the inbound audio segments are staggered, say 50% of sessions are listening to inbound audio (heavy load), while the other 50% is outbound audio.  This can be done dynamically and selectively for the in-flight calls
